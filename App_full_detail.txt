 1. What Is This App?

**EHH (Earth for Humans and Humanity)** is a full-stack social media web application built for students. Think of it as a private Instagram-style platform where students of the same institution can share posts, stories, follow each other, message each other, and interact — all within a closed, admin-moderated environment.

## 5. Real-time System — Socket.io Events

Socket.io runs alongside the Express server on the same port. When a user logs in, their browser opens a persistent WebSocket connection.

**Events the server listens to:**
- `register` — user tells server their userId so server maps userId → socketId
- `sendMessage` — user sends a message, server saves it and forwards to receiver
- `typing` — user is typing, server tells receiver to show typing indicator
- `markAsRead` — user opened chat, server marks messages as read and tells sender

**Events the server emits to clients:**
- `receiveMessage` — new message arrived
- `messageSent` — confirms your message was saved
- `userTyping` — someone is typing to you
- `messagesRead` — your messages were read
- `userStatusUpdate` — user came online or went offline
- `notification` — new like/follow/comment notification in real-time

## 6. Authentication System — How It Works

1. User registers → password hashed with bcrypt (12 salt rounds) → stored in DB
2. On login → bcrypt compares entered password with hash → if match, creates JWT token
3. JWT token contains `{ userId, role }` and expires in 30 days
4. Every protected API request must send `Authorization: Bearer <token>` header
5. `checkUserRestriction` middleware verifies the JWT on every protected route
6. If user is banned → returns 403. If token invalid → returns 401

**Forgot Password flow:**
1. User enters email → server generates 6-digit OTP
2. OTP is hashed with bcrypt and stored in DB with 15-minute expiry
3. OTP is emailed via Resend API
4. User enters OTP → server compares hash → unlocks if correct
5. After 5 wrong OTP attempts → account locked for 30 minutes
6. After OTP verified → user enters new password → bcrypt hashed and saved

## 7. Image Detection System — How It Works

This is your most unique feature. When any post is uploaded:

1. Image is saved to Cloudinary first
2. Background process downloads the image into server memory
3. Sharp resizes it to exactly 64×64 pixels and converts to PNG
4. `image-hash` library runs Perceptual Hash (pHash) algorithm → generates a 64-character hex fingerprint
5. This fingerprint is saved in `Post.phash` column in the database
6. The system compares this hash against every other post's hash using Hamming Distance
7. If similarity score is above 80%, an `ImageMatch` record is created

**In the admin panel:** Admin uploads any image → system compares it against all posts in the database → returns matches sorted by similarity percentage. This catches screenshots, crops, and lightly edited reposts.

## 8. Security Layers

A professional will definitely ask about security. Your app has:

- **JWT authentication** — stateless tokens, 30-day expiry
- **bcrypt password hashing** — 12 salt rounds (industry standard)
- **Helmet.js** — sets 15+ HTTP security headers automatically
- **CORS whitelist** — only your specific frontend domain can call the API
- **Rate limiting** — 200 requests/minute general, 10 login attempts/15 mins, 3 OTP emails/hour, 20 uploads/10 mins
- **Input sanitization** — express-mongo-sanitize strips injection characters
- **Body size limit** — 20MB maximum per request
- **Admin double authentication** — needs JWT AND a secret key header
- **OTP brute force protection** — locks after 5 wrong attempts for 30 minutes
- **Error message sanitization** — raw error details hidden in production

## 11. Questions a Professional Engineer Will Ask — With Your Answers

**Q: How do you handle scalability for 10k users?**
A: Cursor-based pagination on feed instead of offset (doesn't slow down with more data). React Virtuoso for virtual scrolling so the browser only renders visible posts. Database indexes on all frequently queried columns. In-memory cache with 30-second TTL for hot endpoints. Rate limiting to prevent server overload.

**Q: How do you store images?**
A: Multer receives the image buffer in memory, it never touches disk. It is uploaded directly to Cloudinary via their Node.js SDK stream. Cloudinary handles CDN delivery, resizing, and optimisation globally.

**Q: How does real-time messaging work?**
A: Socket.io maintains a persistent WebSocket connection per user. The server keeps a Map of userId to socketId. When user A sends a message, the server saves it to PostgreSQL then emits it directly to user B's socket. If user B is offline, they get the message via REST API when they reconnect.

**Q: What database and why PostgreSQL?**
A: PostgreSQL hosted on Supabase. Relational database chosen because all data has clear relationships — users have posts, posts have likes, users follow users. Prisma ORM handles all queries with type safety. Supabase provides connection pooling via the `DIRECT_URL` setting which is critical for serverless/Render deployments.

**Q: How do you prevent abuse?**
A: Rate limiting per endpoint category, JWT authentication on all write operations, bcrypt for passwords, Helmet for HTTP headers, input sanitization, admin moderation system with audit logs, user ban system with temporary and permanent options.

**Q: What is the unique pHash feature?**
A: When any image is uploaded, the server generates a perceptual hash fingerprint using the pHash algorithm. This fingerprint stays similar even if the image is cropped, screenshotted, or lightly edited. Admins can upload any image and the system compares it against all posts using Hamming Distance to find duplicates with a confidence percentage score.

**Q: How is the app deployed?**
A: Backend runs on Render (Node.js server). Frontend is built with Vite and served as static files. Database is on Supabase (PostgreSQL). Images are on Cloudinary. All three services are free tier capable for initial launch.
